## 0. 이력서와 경력기술서의 역할 분담

지금 가지고 있는 `index.html`은 **이력서**다. 경력기술서는 그것의 확장판이 아니라 **역할이 다른 문서**다.

| | 이력서 (`index.html`) | 경력기술서 (새로 쓸 문서) |
|---|---|---|
| 읽는 시간 | 30초~1분 스캔 | 5~10분 정독 |
| 읽는 사람 | 리크루터 + 면접관 1차 필터 | 면접관, 면접 직전/중 |
| 담는 것 | 결론(성과 수치)과 기술 스택 | 결론에 이르기까지의 **문제·판단·과정** |
| 프로젝트당 분량 | 3~4줄 | 반 페이지~1페이지 |
| 실패 모드 | 길어서 안 읽힘 | 얕아서 면접 질문에 못 버팀 |

**핵심:** 경력기술서는 사실상 **면접 질문의 대본**이다. 면접관은 여기 적힌 문장을 그대로 집어서 "이거 왜 이렇게 하셨어요?"라고 묻는다. 그래서 S2가 말하는 "눈감고도 설명할 수 있어야 한다"는 조건이 분량이나 화려함보다 먼저다.

## 1. 핵심 원칙 9가지 (6개 자료의 교집합)

### 원칙 1. 업무 나열이 아니라 "문제 → 해결 → 결과"로 쓴다 (전 자료 공통)

가장 흔한 탈락 사유. S1은 "관리자 페이지 구축, 결제 모듈 개발" 같은 **수행 업무 나열**을 탈락 패턴 2번으로 지목한다.

- ❌ `ETL 파이프라인 개발`
- ✅ `일 단위 수집 지연이 발생하던 ETL 파이프라인을 병렬 처리 구조로 재설계해 적재 시간을 단축` (S4)

### 원칙 2. "무엇을 만들었나"보다 "왜 그렇게 만들었나" (S1, S4)

S1의 지적이 지금 시점에서 가장 중요하다 — **AI 도구로 코드 작성 자체는 쉬워졌기 때문에, 채용 판단 기준이 구현에서 판단으로 옮겨갔다.** 면접관은 Action(실행)보다 Analyze(대안 검토)를 본다.

기술 스택을 적을 때는 도구명만 나열하지 말고 **도입 배경과 대체안을 제외한 이유**를 함께 적는다 (S4).

- ❌ `Redis 캐시 적용, MySQL 쿼리 최적화`
- ✅ `피크 타임 요청 증가로 지연 발생 → Memcached 대비 Redis 선택(데이터 구조 유연성) → 응답 속도 1.8초 → 420ms 단축` (S1)

### 원칙 3. 성과는 반드시 정량화한다 (전 자료 공통)

"효율 개선" 같은 표현은 정보량이 0이다. 시간/비율/건수/비용 중 하나로 환산한다.

- ❌ `개인화 추천 배치 성능 개선`
- ✅ `개인화 추천 배치를 6시간 10분 → 2시간 50분으로 단축`

**정확한 수치가 없을 때** (S4): "약", "수준", "기존 대비" 같은 표현을 써도 되지만, **산출 근거를 반드시 따로 메모해둔다.** 면접에서 "그 88%는 어떻게 계산하셨어요?"는 거의 확정적으로 나오는 질문이다.

> ⚠️ 특히 **100%를 넘는 비율(예: 240% 향상, 230% 상승)은 위험도가 높다.** 분모가 무엇인지 모호하면 신뢰를 잃는다. `240% 향상` 대신 `신규 파이프라인 1건 개발 공수 5일 → 1.5일` 처럼 **절대값 before/after**로 쓰는 편이 항상 안전하다.

**데이터 엔지니어가 반드시 채워야 할 정량화 5축** (S6). 이 다섯 가지 중 최소 3개가 문서 전체에 등장해야 한다.

| 축 | 표현 예 |
|---|---|
| ① 데이터 규모 | 일 N억 건, N TB/PB, 소스 N개, 테이블 N개 |
| ② 안정성 | 파이프라인 성공률, SLA 준수율, 장애 건수 감소, 가용률 |
| ③ 데이터 품질 | 정합성 오류율, 중복률, 검증 룰 커버리지, 이상 탐지 건수 |
| ④ 비용 | 스토리지/컴퓨팅 비용 절감액·절감률 |
| ⑤ 속도 | 배치 수행 시간, 적재 지연(latency), 배포 사이클 |

S6은 특히 **배치와 실시간 처리 경험을 모두 보여주는 것(다재다능함)**을 강조한다. 둘 중 하나만 있으면 담당 가능한 범위가 좁게 읽힌다.

### 원칙 4. 규모와 컨텍스트를 명시한다 (S4)

DE 직무에서 "파이프라인을 만들었다"는 문장은 규모 없이는 난이도를 알 수 없다. 프로젝트마다 다음 중 해당하는 것을 적는다.

- 일 처리 건수 / 데이터 볼륨 (TB, PB, 일 N억 건)
- 테이블 수, DAG 수, 소스 시스템 수
- 클러스터/노드 규모, 동시 사용자 수
- 팀 규모와 본인 포지션

### 원칙 5. 본인이 한 일만, 본인 기여도를 명확히 (S2, S4)

> "남들이 수행한 일이 아닌 내가 수행한 일들과 해결과정을 써내려가라" (S2)

- 역할은 **설계 주도 / 부분 개발 / 운영** 중 어디인지 구분해서 쓴다 (S4).
- 기여도는 **백분율(예: 기여도 70%)로 쓰지 말고 서술형으로** 쓴다 (S2). "3인 팀에서 수집 계층 설계와 커넥터 개발을 담당" 이 "기여도 60%"보다 훨씬 신뢰가 간다.
- **본인 역할이 작은 프로젝트는 과감히 뺀다** (S2). 목록이 길어질수록 주력이 흐려진다.

### 원칙 6. 설명할 수 없는 건 쓰지 않는다 (S2, S3, S4)

S4의 실전 팁: **문장마다 후속 질문 2개를 가정해본다.** 답이 막히면 그 문장은 수정하거나 뺀다.

써놓고 답을 준비해야 할 대표 질문 유형:
- "왜 A 대신 B를 선택했나요?"
- "그 수치는 어떻게 측정했나요?"
- "그 방식의 단점/한계는 뭐였나요?"
- "다시 한다면 어떻게 하시겠어요?"

### 원칙 7. 디테일은 '핵심 개념' 수준까지만 (S3)

원칙 2와 균형을 잡아야 한다. **판단 근거는 깊게, 구현 세부는 얕게.**

- ❌ `knative의 hpa 기능을 이용하여 cpu metric을 기준으로 한 autoscaling을 적용함...` (구현 세부 과잉)
- ✅ `Kafka를 이용한 실시간 Event Pipeline 관리 및 failover-pipeline으로 Kinesis를 사용하여 안정성 극대화, 결과 99.9991% 이상의 가용률 달성` (S3)

판단 기준: **그 문장이 "내가 무엇을 판단했는가"를 담고 있으면 남기고, "도구를 어떻게 설정했는가"만 담고 있으면 줄인다.**

### 원칙 8. 협업과 커뮤니케이션을 드러낸다 (S1)

S1의 탈락 패턴 3번. 기술만 있고 사람이 없는 경력기술서는 시니어 레벨에서 특히 불리하다.

- 요구사항이 모호했던 상황을 어떻게 정리했는지
- 다른 팀(분석가/기획/PM)의 반복 요청을 어떻게 구조적으로 없앴는지
- 표준·가이드·문서로 팀 전체 생산성을 어떻게 올렸는지

### 원칙 9. 기술을 '사업 언어'로 번역한다 (S5)

S5는 평가자가 확인하려는 질문을 이렇게 정리한다 — **"이 지원자가 복잡한 데이터 흐름을 운영 가능한 시스템으로 만들 수 있는가."** 따라서 도구 경험이 아니라 **문제를 시스템 관점에서 해석한 흔적**이 차별화 요소가 된다.

- ❌ `Airflow를 썼다` / `Spark를 사용했다` — 도구명만, 맥락도 성과도 없음
- ❌ `의존성이 복잡한 DAG를 구축했다` — 설명 없이 난이도만 주장
- ✅ `일 배치 의존 구조를 CDC 기반으로 전환해 지연 시간을 줄이고 운영팀의 수동 확인 절차를 줄였다` — 문제 → 전환 방식 → 효과가 한 문장에

두 번째 나쁜 예가 특히 중요하다. **"복잡했다", "대규모였다", "어려웠다"는 형용사는 난이도를 주장할 뿐 증명하지 않는다.** 복잡도는 숫자(테이블 수, 의존 깊이, 소스 수)로만 증명된다.

기술 성과는 항상 **"그래서 사업/조직에 무엇이 좋아졌는가"**까지 연결한다. `적재 지연 6시간 → 30분`에서 끝내지 말고 `→ 마케팅팀이 당일 캠페인 성과를 당일에 확인 가능해짐`까지 붙인다.

## 2. 표준 서술 프레임: PAAR

S1의 프레임워크가 가장 명료하고, S4의 "문제-행동-성과"와 S2의 6대 구성요소를 모두 포섭한다.

```
P — Problem   : 어떤 문제/병목/비용이 있었는가 (숫자로)
A — Analyze   : 어떤 선택지가 있었고, 왜 이걸 골랐는가  ← 면접관이 가장 주목하는 구간
A — Action    : 무엇을 설계하고 구현했는가 (본인이 한 것만)
R — Result    : 무엇이 얼마나 달라졌는가 (숫자로)
```

**대부분의 경력기술서가 A(Analyze)를 빼먹는다.** P-A-R만 있으면 "일 잘하는 사람"으로 보이고, Analyze가 있으면 "판단할 줄 아는 사람"으로 보인다. 5년차 이상에서 이 차이가 합격/불합격을 가른다.

### 보강: S5의 4단계 구조

S5는 Problem과 Analyze 사이에 **"원인 가설"** 단계를 하나 더 둔다. 데이터 엔지니어에게는 이 단계가 특히 중요하다 — **증상을 보고 원인을 좁혀간 과정 자체가 진단 역량의 증거**이기 때문이다.

```
1. 문제를 수치나 현상으로 정의     ← "느려졌다"가 아니라 "6시간 10분 걸렸다"
2. 원인 가설을 어떻게 세웠는가     ← Spark UI, 실행계획, 파티션 스큐 확인 등
3. 대안 간 선택 기준 제시          ← 비용/운영부담/팀역량/기존스택 호환
4. 적용 후 성능·안정성·운영 편의 개선 결과 정리
```

2번은 **"왜 그게 원인이라고 판단했는가"**다. 예를 들어 "배치가 느려서 병렬화했다"는 약하고, "Spark UI에서 특정 스테이지가 전체 시간의 70%를 점유하고 파티션 스큐가 확인되어, 병렬화보다 리파티셔닝이 우선이라고 판단했다"는 강하다. **경력기술서에서 2번이 있는 프로젝트가 하나라도 있으면 문서 전체의 신뢰도가 올라간다.**

권장: 전 프로젝트에 2번을 다 넣을 필요는 없고, **가장 자신 있는 성능/장애 프로젝트 1~2개에 집중적으로** 넣는다.

## 3. 프로젝트 1건 작성 템플릿

S2의 6대 구성요소를 PAAR에 맞춰 정리한 형태다.

```markdown
### [프로젝트명 — 내 역할이 드러나게]
**기간** 2025.09 ~ 2025.12 (4개월)
**역할** 설계 주도 / N인 팀, 수집·적재 계층 담당
**규모** 소스 N개, 테이블 N개, 일 N억 건 / N TB

**배경 및 문제**
(2문장 이내. 무엇이 얼마나 아팠는지를 숫자와 함께.)

**기술적 판단**
- 검토안: A / B / C
- 선택: B — 이유 (비용, 운영 부담, 팀 역량, 기존 스택 호환성 등)
- 배제: A — 이유 / C — 이유

**수행 내용**
- (본인이 설계·구현한 것 중심으로 3~5개)

**성과**
- (before → after 절대값 우선, 비율은 보조)

**한계 및 배운 점** (선택)
- (남은 과제를 스스로 아는 것도 시니어 신호)
```

> **팁 (S2):** 프로젝트 제목은 사내 공식 명칭 그대로가 아니라 **내 역할이 드러나도록 조금 바꿔도 된다.**
> 예: `데이터 파이프라인 전환` → `Fivetran → Airbyte 자체 운영 전환을 통한 ETL 비용 구조 재설계`

**JD 용어와 맞춘다 (S6):** 핵심 역량 키워드는 지원하는 공고의 용어와 **정확히 같은 표기**로 쓴다. 검증 가능한 키워드(Python, SQL, Spark, Airflow, Kafka, AWS)를 앞에 둔다. 회사마다 JD가 다르므로, 경력기술서는 **한 벌을 만들어두고 지원 시 상단 요약과 키워드만 갈아끼우는** 구조로 설계하는 편이 효율적이다.

## 7-1. 경력기술서에 담아야 할 '4종 소재' (S5)

S5가 제시한 면접 준비 체크리스트는 사실상 **경력기술서에 반드시 들어가야 할 소재 목록**이다. 프로젝트 나열만 하면 이 중 3개가 빠진다.

| 소재 | 담는 법 |
|---|---|
| ① 대표 프로젝트 (3분 설명 분량) | 가장 잘 아는 것 1개를 **가장 길게**. 문서의 중심축 |
| ② **장애 사례** (원인 → 대응 → 재발 방지) | 별도 항목으로 빼도 좋다. 대부분의 지원자가 빼먹는 영역이라 차별화가 크다 |
| ③ 성능 개선 사례 | 위 4단계 구조(특히 원인 가설)를 적용할 최적의 소재 |
| ④ 기술 선택 근거 | 원칙 2의 Analyze. 프로젝트마다 최소 1개 |
| ⑤ 협업 구체 사례 | 원칙 8. 조직 간 합의·표준화 경험 |

> **장애 사례는 마이너스가 아니라 플러스다.** "장애를 낸 적 없다"는 답은 규모 있는 시스템을 운영해본 적 없다는 뜻으로 읽힌다. **원인 분석과 재발 방지 조치**까지 쓰면 신뢰성이 크게 올라간다.

## 8. 최종 셀프 체크리스트

초안을 다 쓴 뒤 프로젝트마다 아래를 통과시킨다.

**프로젝트 단위**
- [ ] 문제(P), 대안 검토(A), 실행(A), 결과(R) 네 가지가 모두 있는가 (S4의 "문제·역할·기술 판단·결과" 4요소와 동일)
- [ ] 기간(월 단위 + 총 소요기간)이 있는가
- [ ] 규모(볼륨/건수/테이블 수/팀 인원)가 있는가
- [ ] 내 역할이 설계 주도/부분 개발/운영 중 무엇인지 명시했는가
- [ ] 성과가 숫자인가, 그리고 그 숫자의 산출 근거를 내가 말할 수 있는가
- [ ] 100% 넘는 비율 표현이 있다면 절대값 before/after로 바꿀 수 있는가

**문장 단위**
- [ ] 이 문장에 후속 질문 2개를 던졌을 때 답할 수 있는가
- [ ] 도구 이름만 있고 판단이 없는 문장은 아닌가
- [ ] 구현 세부가 과한 문장은 아닌가 (설정값·옵션명 나열)
- [ ] 내가 한 일인가, 팀이 한 일인가

**문서 단위**
- [ ] 프로젝트 5~10개 이내인가
- [ ] 최신순인가
- [ ] 문체와 포맷이 일관적인가
- [ ] 협업/표준화 관점 문장이 최소 몇 개 있는가
- [ ] 이력서(index.html)의 수치와 100% 일치하는가
- [ ] 정량화 5축(규모/안정성/품질/비용/속도) 중 최소 3축이 등장하는가
- [ ] **장애 대응 사례**가 최소 1건 있는가 (원인 → 대응 → 재발 방지)
- [ ] 배치와 실시간 처리 경험이 **둘 다** 드러나는가
- [ ] "복잡한", "대규모의", "어려운" 같은 형용사로 난이도를 주장한 곳은 없는가 (숫자로 대체)
- [ ] 기술 성과가 사업/조직 효과까지 연결되는가

## 9. 현재 이력서 기준 적용 노트

`korean/index.html`을 읽고 본, 경력기술서로 확장할 때의 우선순위다.

**강점 — 그대로 살릴 것**
- 성과 수치 밀도가 높다 (88% 절감, 6시간10분→2시간50분, 55% 절감, 5배 단축). 원칙 3을 이미 잘 지키고 있다.
- 도메인별 1등 기업 + DAU 규모를 회사 설명에 넣은 것은 좋은 컨텍스트 제공이다.
- 최근 프로젝트(DataHub + LLM/MCP 메타데이터 자동화)는 차별화 포인트가 확실하다. 경력기술서에서 가장 길게 써야 할 항목.

**보완 1 — Analyze(대안 검토)가 거의 없다 (가장 큰 갭)**
현재 이력서 전체에서 "왜 그 선택이었나"가 드러나는 문장이 사실상 없다. 경력기술서에서 반드시 채워야 할 것:
- Fivetran → **왜 Airbyte인가?** (Meltano, dlt, 자체 구축, Fivetran 요금 재협상 대비)
- Airbyte OSS를 **왜 EKS 위에서 직접 운영**하기로 했나? (Cloud 대비 운영 부담 vs 비용)
- Airflow를 **왜 K8s(MSA)로** 옮겼나? (Celery Executor 유지 대비)
- EMR 스팟 인스턴스 — **중단 리스크를 어떻게 감수/완화**했나?
- DataHub — **왜 DataHub인가?** (OpenMetadata, Amundsen, Collibra 대비)

**보완 2 — 산출 근거가 위험한 수치**
- `개발 속도 240% 향상` — 분모가 뭔지 불명확. 절대값(예: 신규 DAG 1건 개발 N일 → M일)으로 바꾸는 것을 권장.
- `VOC 대응 속도 230% 상승` — 동일. `평균 인지 시간 N시간 → M시간`이 안전.
- `DAG 배포 속도 15% 향상` — 15%는 임팩트가 작아 보여서 오히려 손해. 절대 시간이나 다른 효과(배포 실패율, 수동 개입 제거)로 재구성 검토.
- `88% 절감` — 강력한 수치인 만큼 반드시 계산식(월 $X → $Y, 인건비 포함 여부)을 준비.

**보완 3 — 규모와 역할 정보 부재**
프로젝트별로 기간, 팀 인원, 본인 포지션, 데이터 규모가 하나도 없다. About Me의 "TB/PB 단위"를 프로젝트별로 분해해서 배치할 것.

**보완 4 — 확인이 필요한 사항**
- 이력서상 `5년차`인데 경력 시작이 2021.01이면 2026년 기준 6년차다. 표기 기준을 정리할 것.
- 웅진씽크빅 종료(2024.12)와 NSUS 입사(2025.09) 사이 약 8개월 공백이 있다. 경력기술서 자체에 쓸 필요는 없지만 **설명은 반드시 준비**해야 한다 (학습·자격증·개인 프로젝트로 채울 수 있으면 좋다. AWS DEA 자격증 2026.02 취득이 있으니 연결 가능).
- 오타: Skills의 `Git/Github Adction` → `Actions`.

**보완 5 — 협업/커뮤니케이션 (S1 탈락 패턴 3)**
비투엔 시절 GS Retail/GS Shop 거버넌스 프로젝트는 사실상 **조직 간 합의를 이끌어낸 경험**인데 현재는 기술 작업처럼만 적혀 있다. "도메인별로 다르게 쓰던 용어를 어떻게 합의시켰는가"를 풀면 5년차 구간에서 가장 강력한 소재가 된다. 백오피스 개발 관련 팀 내 제안 경험(About Me에만 있음)도 프로젝트로 승격할 만하다.

**보완 6 — 장애 사례가 0건이다 (S5)**
현재 이력서 8개 프로젝트 어디에도 장애/트러블슈팅 소재가 없다. TB/PB 규모를 5년간 운영했다면 반드시 있을 텐데, 경력기술서에서 **원인 → 대응 → 재발 방지** 구조로 최소 1건을 넣으면 차별화 효과가 크다. (예: Airbyte 커넥터 실패, EMR 스팟 인스턴스 회수, Kafka 컨슈머 랙, 규제 리포트 오전송 — 마지막 항목은 이미 "잘못 전송된 대규모 과거 데이터의 추적 및 보정"으로 이력서에 흔적이 있다.)

**보완 7 — 실시간 처리 경험이 묻혀 있다 (S6)**
Kafka가 기술 태그에만 있고 실시간 파이프라인을 설계·운영한 서술이 없다. S6의 "배치+실시간 다재다능함" 기준에서 손해다. Kafka로 무엇을 했는지 명시적으로 풀 것.

## 10. 문서 배치 결정: 별도 페이지(`/korean/details/`) 권장

**결론: 이력서와 경력기술서를 물리적으로 분리하고, 이력서에서 앵커 딥링크로 연결한다.**

```
/korean/                     이력서 (현행 유지, 1~2p)
/korean/details/             경력기술서 (신규, 5~10p)
/english/  ·  /english/details/   동일 구조
```

**왜 아코디언(펼치기)이 아니라 별도 페이지인가**

| 기준 | 별도 페이지 | 한 페이지 아코디언 |
|---|---|---|
| PDF 저장 | 각각 목적에 맞는 A4 출력. 채용 사이트가 이력서/경력기술서를 따로 요구할 때 그대로 대응 | `@media print`에서 접힌 영역을 강제로 펼쳐야 하고 page-break 제어가 어려움. 한 PDF에 두 문서가 섞임 |
| 리크루터 스캔 | 이력서가 1~2p로 유지됨 | 펼치면 스캔 불가, 접으면 **안 읽힘**(리크루터는 클릭하지 않는다) |
| 문서 역할 | §0의 역할 분담과 일치 | 두 목적이 한 문서에서 충돌 |
| 유지보수 | 경력기술서를 원본(single source of truth)으로, 이력서를 요약본으로 관리 | 한 파일이 계속 비대해짐 |

**분리의 단점(통합감 상실)은 이렇게 상쇄한다**

1. 이력서의 각 프로젝트 제목 옆에 `상세 →` 링크 → `/korean/details/#airbyte-migration` 같은 **앵커 딥링크**로 해당 항목에 바로 착지
2. 경력기술서 상단에 `← 이력서로 돌아가기`
3. 이력서 Experience 섹션 헤더 옆에 `전체 경력기술서 보기 →` 한 줄
4. 인쇄 시 링크가 죽으므로, 이력서 print CSS에서 상세 페이지 URL을 텍스트로 노출시킬 것

**프로젝트별 개별 페이지(`/korean/details/airbyte`)는 권하지 않는다.** PDF 한 벌로 저장하기가 다시 어려워지고, 관리할 파일 수만 늘어난다.

**구현 메모**
- GitHub Pages는 `korean/details/index.html`을 두면 `/korean/details` 접근 시 `/korean/details/`로 리다이렉트한다. 파일 위치는 `korean/details/index.html`.
- 현재 `index.html`의 print CSS(`zoom: 0.85`, `break-inside: avoid`)는 그대로 재사용하되, 경력기술서는 페이지가 길어지므로 프로젝트 단위 `break-before: page` 검토.
- 작성 순서는 **경력기술서 → 이력서** 순. 상세를 먼저 확정하고 거기서 수치를 뽑아 이력서를 갱신해야 수치 불일치가 안 생긴다.
