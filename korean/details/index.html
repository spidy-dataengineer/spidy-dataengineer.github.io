전환 전 비즈니스 DB 63개(MSSQL · MySQL · PostgreSQL) → Fivetran(row 단위 종량 과금) → Snowflake DW · Mart
전환 후 동일 소스 → Airbyte OSS on EKS → 검증 → DBT 변환 → Snowflake DW · Mart (기존 스키마 유지)

배경 및 문제

Fivetran은 row가 insert · update · delete될 때마다 과금되는 종량제 구조여서 데이터 증가에 비례해 비용이 선형 증가했고, 이 규모에서는 지속 가능하지 않았다. 다만 이미 구축된 DW · Mart가 Fivetran 산출물의 컬럼 구조에 의존하고 있어, 전환 후에도 동일한 형식이 유지되어야 다운스트림을 건드리지 않을 수 있었다.

기술적 판단
  • Airbyte OSS 자체 운영(EKS) — 처리량 비례 종량 과금에서 서버 비용만 발생하는 고정비 구조로 전환. 운영 부담을 팀이 흡수하는 대신 데이터 증가가 비용 증가로 직결되지 않는 구조를 확보
  • Airbyte 산출물을 DBT로 재변환 — Airbyte는 원천 데이터 타입이 의도한 대로 매핑되지 않았다. 그대로 적재하면 다운스트림 컬럼 정의를 전부 고쳐야 하므로, DBT 계층에서 Fivetran과 동일 형식으로 맞춰 다운스트림 수정 없이 전환
수행 내용
  • 동적 DAG 생성 모듈 개발 — Airbyte 적재 → 검증 → DBT 변환 파이프라인을 자동 생성하여 커넥터 160개를 개별 DAG 작성 없이 처리
  • Cosmos PoC를 거쳐 DBT를 Airflow 내에서 실행하도록 구성, Airflow on K8s 구축 및 EKS 자원 관리
  • MSSQL Change Tracking custom connector 개발 — Fivetran이 지원하던 CT를 Airbyte 표준 커넥터가 지원하지 않아 직접 구현
  • Cursor 증분 적재 누락 진단 및 해결 — 날짜 컬럼의 소수점 정밀도가 낮아 동일 시각 row가 다수 존재했고, 배치가 일부만 읽고 그 시각을 기준점으로 기록하면 다음 배치가 ‘초과’ 조건으로 나머지를 건너뛰었다. 기준을 ‘이상’으로 바꿔 dedup으로 제거 가능한 중복을 감수하고 복구 불가능한 누락을 차단
  • Airbyte · Airflow API 연동으로 운영 중인 파이프라인 목록을 1시간 단위 Google Sheet 자동 갱신
  • Test · Stage 환경 마이그레이션 (Prod 및 인프라 · 네트워크는 팀원 담당)
성과 및 한계

배경 및 문제

전 세계 10여 개국 규제 당국이 각기 다른 스펙과 전달 방식으로 데이터 제출을 요구하며, 잘못 제출하면 정정 요구와 제재로 이어지는 도메인이다. 담당한 네덜란드 · 스웨덴 · 필리핀 3개국은 요구 방식이 서로 달라 국가마다 다른 전달 채널이 필요했다.

특히 네덜란드는 일 100만 건 규모의 레거시 리포팅 시스템으로, 기능이 추가될 때마다 예외 처리가 기존 로직 사이에 덧붙여져 누락 케이스가 생겼고, Kafka 소스 오류와 비동기 소비 구조상 순서 미보장으로 잘못된 데이터가 그대로 전송되는 일이 반복됐다. 규제 당국의 inquiry가 오면 수동 재전송과 버그 수정이 주 업무였다.

기술적 판단
  • 전송 포맷은 못 바꾸므로, 조회 가능한 형태를 원본으로 둔다 — SOAP 규격상 XML 전송이 강제되어 포맷 자체는 고정이었다. 대신 전송될 내용을 JSON으로 테이블에 보관하고 XML은 그로부터 생성되는 파생물로 두어, 이력 조회와 재전송이 같은 소스에서 이뤄지도록 설계
  • 실시간 · 준실시간 경로를 단일 테이블로 통합 — 두 경로가 나뉘어 있어 과거 이력을 한 번에 조회할 수 없었으므로, 이력 추적과 재처리의 기준점을 하나로 통합
  • 전달 채널은 국가별로 분리하되 데이터는 공통 마트에서 공급 — 리포트 스펙은 다르지만 player status · wallet 등 기반 도메인은 공유하므로, 공통 마트 위에서 국가별 스펙으로 변환. 네덜란드·스웨덴이 우리가 데이터를 내보내는 방식인 것과 달리 필리핀은 규제 당국이 필요할 때 직접 조회해 가는 방식이고 실시간 요건도 없어, 상시 서버 대신 Serverless로 구성해 대기 비용 제거
장애 대응 — 과거 리포팅 데이터 전수 조사 및 정합성 검증
  • 현상 · 원인 — 규제 당국 inquiry로 제출 데이터 오류가 지적됨. 예외 처리 누락, Kafka 소스 오류, 비동기 소비로 인한 순서 미보장이 복합 작용
  • 진단의 난점 — 정확한 확인은 실제 전송된 XML을 봐야 가능한데, 그 XML이 1파일 1record 단위로 S3 단일 폴더에 수천만 개 파티셔닝 없이 쌓여 있어 특정 구간만 보려 해도 전수 스캔이 필요했다
  • 실행 환경 판단 — Glue는 소형 파일을 한 파티션으로 묶어 읽는 기능이 있어 유리했으나 XML 리더가 네임스페이스 제거를 지원하지 않아 태그 정제가 불가능했다. 파싱이 선행 조건이므로 소형 파일 최적화를 포기하고 EMR Serverless에서 파싱을 직접 제어하는 쪽을 선택
  • 그 대가로 Glue가 자동 처리하던 소형 파일 대응을 직접 구성 — driver 단독 리스팅으로 메모리 부족이 반복되어 리스팅을 worker에 분산하고 입력 파티션 크기를 축소. root tag 네임스페이스는 S3 객체 앞부분만 Range 요청으로 읽어 종류를 수집한 뒤 태그별로 읽어 병합. 파일 경로를 미리 수집해 목록으로 넘기는 방식도 검토했으나, 경로를 명시하면 파일마다 크기를 개별 조회해야 해 실측 결과 오히려 느려 경로 단위 로드를 유지 → 조사 대상 2년치 1,170만 건 전수 파싱 약 2시간
  • 재조사 가능한 구조로 전환 — 리포트 유형 · 기준일자 2단계 파티셔닝 Parquet 적재, RDB 적재 후 최신 전송분만 남기도록 중복 제거 및 인덱스 구성, Snowflake 주기 적재. 원천과 송신 데이터를 대조해 오류를 식별하고 Replacement · Cancellation으로 정정

배경 및 문제

도메인 특화된 컬럼과 비즈니스 용어가 다수 존재했고, 같은 용어가 팀마다 다른 정의로 사용되어 사람 간에도 해석이 갈렸다. 더 직접적인 문제는 AI가 그 의미를 추론에 의존해 사용하고 있었다는 점이다. 기준 정의가 없으니 이름과 맥락으로 짐작할 수밖에 없었고 결과의 정확도가 낮았다. 사람 간 이해를 통일하는 것과 AI가 참조할 기준을 만드는 것이 같은 문제였다. 또한 데이터 흐름이 추적되지 않아 장애·변경 시 영향받는 downstream을 파악할 수단도 없었다.

기술적 판단
  • 카탈로그 솔루션은 DataHub로 이미 선정된 상태였으므로, 도구 선택이 아니라 정의가 실제로 신뢰받고 활용되는 구조를 만드는 데 집중
  • LLM 초안 + 팀 확정 구조 — 테이블 수천 개 규모에서 전량 수기 작성은 불가능했고, 반대로 LLM 생성물을 그대로 두면 검증되지 않은 정의가 기준처럼 쓰일 위험이 있었다. 사내 Confluence의 기존 용어를 근거로 초안을 생성하되 확정 권한은 데이터를 만드는 팀에 두어 분리
  • 초안과 확정을 구분 표시하고 그 상태를 AI도 확인 가능하게 — 검수 완료 후 공개하면 카탈로그가 오래 비고, 구분 없이 공개하면 미검수 정의가 기준으로 오인된다. 상태를 함께 노출해 초안도 활용하되 신뢰 수준을 판단할 수 있게 하고 확정 범위를 점진 확대하는 방식을 선택
  • 카탈로그를 문서가 아니라 도구가 조회하는 소스로 규정 — MCP로 AI가 질의 시점에 정의를 직접 참조하도록 연결. 단일 진실 원천은 DataHub로 고정하고 Snowflake 컬럼 comment는 그 정의를 반영한 결과로 두어 다중 관리로 어긋나는 상황을 차단

ETL 파이프라인 성능·비용 최적화 및 표준화·자동화

  • 기간2023.12 - 2024.04 (5개월)
  • 역할설계·개발 전담 (동료 리뷰·승인)

전환 전 직렬 실행 · 종료 시각 기반 배치 의존 · 수동 적재(TSV/Parquet 변환 · Glue Crawler) · DB Procedure 기반 ETL 로직
전환 후 TaskGroup 병렬 실행 · Sensor/Trigger 기반 의존 · Dynamic DAG 자동 생성 · SQL 파일 형상관리 · 사내 데이터 포털 연계 등록

배경 및 문제

배치 지연의 주된 원인이 두 곳이었다. DAG 안에서는 의존 관계가 없는 작업까지 하나씩만 실행되어 불필요한 대기가 쌓였고, DAG 사이에서는 선행 작업의 ‘예상 종료 시각’에 맞춰 후행을 거는 방식을 쓰고 있었다. 후자는 의존 관계를 선언한 것이 아니라 소요 시간을 어림잡은 것이어서, 선행이 늦어지면 후행이 준비되지 않은 데이터를 읽는 구조였다.

또한 ETL 요청마다 최초 적재를 수동 수행(TSV·Parquet 변환, Glue Crawler)했고, 반복되는 파이프라인 코드도 매번 새로 작성됐다. ETL 로직이 DB Procedure에 들어가 있는 경우도 있었는데, 이런 건 변경 이력을 추적할 수단이 없었다.

기술적 판단
  • 암묵적 시간 의존 → 명시적 완료 의존 — 소요 시간을 어림잡아 간격을 두는 방식은 선행이 지연되는 순간 정합성이 깨진다. 간격을 더 벌리면 지연만 커지고 정합성은 여전히 보장되지 않으므로, Sensor · TriggerDagRun으로 실제 완료 여부에 연결해 정합성 확보와 대기 제거를 동시에 달성
  • DAG 내부 지연의 원인은 처리 성능이 아닌 직렬 실행이라 보고, 자원 증설 대신 상호 의존이 없는 작업을 TaskGroup 병렬 구조로 전환
  • 상시 가동 EMR 제거로 비용에 접근 — 클러스터가 24시간 떠 있으면 튜닝으로 줄일 수 있는 폭에 한계가 있다고 보고, 상시 클러스터를 없애고 워크로드 특성에 따라 실행 환경을 분리 (작은 것 → EMR Serverless / 큰 것 → EMR on EC2 스케줄 기동 / 지연 허용 → Spot)
  • DAG를 개별 작성이 아닌 생성 대상으로, 로직은 DB에서 코드로 — 복사·수정 방식은 구조가 제각각이 되고 공수가 반복되므로 표준 포맷 생성 도구를 만들고, Procedure에 있던 로직은 형상관리·리뷰가 가능하도록 SQL 파일로 이관
수행 내용 — 성능 및 비용
  • Spark Job 자원 및 쿼리 튜닝으로 개인화 추천 배치 6시간 10분 → 2시간 50분 — executor당 core·메모리를 표준 산정 공식으로 기준값을 잡고 워크로드에 맞춰 실측 비교하며 조정, EMR 5.x → 6.x 버전업으로 AQE 적용 및 파티션 수 조정

  • 알림 체계 개편 — Slack 단일 채널 → Slack + Email(AWS SES) 이중 발송, 공통 utils 모듈로 표준화. 서비스·테이블명, 데이터 건수, 소요 시간 등 실행 결과를 상세 전송하여 실패 여부만이 아니라 처리 내역을 확인 가능하도록 구성
성과

단일 서버 Airflow의 Kubernetes 무중단 전환 및 운영 표준화

  • 기간2024.05 - 2024.06 (2개월)
  • 역할전환 설계·수행 · 운영 표준 수립
  • 규모이관 DAG 150개

전환 전 EC2 단일 서버 · LocalExecutor · 로컬 PostgreSQL · 로컬 로그 · 수동 배포
전환 후 Kubernetes · KubernetesExecutor · RDS(MariaDB) · S3 Logging · GitSync 자동 동기화

배경 및 문제

EC2 한 대에서 LocalExecutor로 Airflow를 Monolithic하게 운영하고 있었다. 메타DB · DAG 로그 · DAG 파일이 모두 서버 로컬에 묶여 있어 저장 공간이 주기적으로 포화됐고, 그때마다 DAG 로그가 남지 않았다. 결과적으로 에러는 자주 나는데 원인을 확인할 근거가 사라지는 구조였고, 로그를 못 보니 대응이 늦어지고 늦어진 만큼 디스크가 다시 차오르는 상태가 반복됐다.

기술적 판단
  • 근본 원인을 ‘상태가 서버 로컬에 묶여 있는 것’으로 규정. 서버 스펙을 올려서는 재발을 막을 수 없다고 보고, 메타DB · 로그 · DAG 파일을 각각 외부(RDS · S3 · Git)로 분리하는 방향으로 설계
  • LocalExecutor → KubernetesExecutor — 태스크를 Pod 단위로 분리해 DAG 간 자원 간섭을 제거하고 서버 증설 없이 확장 가능한 구조 확보
  • 운영 중인 스케줄러를 한 번에 교체하는 것은 리스크가 크다고 보고 DAG 단위 점진 이관 선택. 리스크가 낮은 DAG부터 신규 환경으로 옮기고 정상 동작이 확인되면 기존 Airflow에서 제거하는 방식으로 병행 운영
  • 전환과 동시에 Airflow 2.1.3 → 2.7.2 버전업 진행 — DummyOperator 폐기 대응, schedule_interval → schedule 전환 등 변경점을 DAG 이전 과정에서 함께 적용하여 인프라 전환과 버전 대응을 DAG 단위로 분리 검증, 문제 발생 시 원인을 좁힐 수 있도록 구성
수행 내용
  • EC2 단일 서버(Monolithic) → Kubernetes(MSA) 전환 및 KubernetesExecutor 적용, DAG 150개 무중단 이관
  • 메타DB를 로컬 PostgreSQL → AWS RDS(MariaDB)로 이관 (사내 표준이자 비용이 낮은 MariaDB로 스택 일원화). 엔진이 달라 덤프·복원 후 마이그레이션 명령으로 스키마를 올리는 표준 경로가 성립하지 않았고 버전업으로 테이블 구조까지 달라져, 기존 메타데이터를 2.7.2 스키마에 맞게 조정해 직접 적재 — 빈 메타DB로 시작하지 않고 과거 실행 이력을 보존해 backfill 판단 근거와 운영 연속성 유지
  • 로컬 Logging → S3 Logging으로 전환하여 디스크 포화와 로그 유실을 동시에 해소
  • GitSync 도입으로 Jenkins 빌드·배포 단계를 거치지 않고 Git 변경이 직접 반영되도록 전환, Helm 기반 인프라 코드화 및 Jenkins · ArgoCD 연계 자동 배포(이미지는 ECR 관리), Grafana · Prometheus 모니터링 도입
  • 운영 표준화 — DAG · 파일 네이밍 컨벤션과 코드 포맷팅 규칙, DAG 자동 생성 및 생성 이력 관리, SQL 파일 형상관리, 프로젝트 폴더 구조 개선, 사용자별 권한 체계 적용
성과 및 한계
  • 로그·메타데이터를 서버 외부로 분리하여 디스크 포화로 인한 로그 유실과 실행 이력 손실을 구조적으로 제거

고객 불만 사항을 빠르게 인지해 대응 부서로 전달하는 것이 목표였다. 근거가 되는 데이터는 사내 5개 플랫폼의 시스템 로그 · 앱 로그 · VOC에 흩어져 있었고, 플랫폼마다 규정과 데이터 템플릿이 달라 사람이 취합해야만 파악이 가능한 상태였다. 그 결과 불만 발생 시점과 대응 부서가 인지하는 시점 사이에 평균 반나절의 간격이 있었고, 취합 과정에서 걸러지지 않으면 몇 개월간 인지되지 못한 채 남는 경우도 있었다.

기술적 판단
  • 처리 도구를 Spark로 통일 — VOC는 데이터량이 적어 Spark가 비용 면에서 효율적인 선택은 아니었으나, 소스별로 다른 처리 도구를 두면 운영·유지보수 부담이 누적된다고 판단해 비용 비효율을 감수하고 전 소스를 Spark / SparkSQL로 통합
  • 통합 마트 스키마 설계 — 공통 필드는 고정 컬럼으로 두고 소스별로 상이한 상세 정보는 DATA 필드에 JSON으로 담는 구조로 설계하여, 플랫폼마다 다른 템플릿을 스키마 변경 없이 수용
  • ML 모델은 KubernetesPodOperator로 격리 실행 — 모델별 의존성이 파이프라인 실행 환경과 충돌하지 않도록 분리
수행 내용
  • 규정과 템플릿이 상이한 사내 5개 플랫폼의 로그·VOC를 S3로 집계하고, Spark / SparkSQL 기반 비정형 텍스트 처리로 정제·통합하여 통합 마트 구성
  • 소스별 추출 rule 설계 — 앱·시스템 로그의 비정형 텍스트는 키워드 기반 정규식으로 구간을 추출하고 CSV로 수집되는 VOC는 필요한 컬럼에서 값만 선별. 추출 결과의 형태가 소스마다 달라 사전 정의한 통합 마트 필드에 매핑하는 기준을 소스별로 따로 잡아야 했다
  • 1시간 단위 준실시간 알림 구조를 구축하여 대응 부서에 자동 전달
  • ML 모델 배포 자동화 — AI 부서가 개발한 VOC 텍스트 분류 모델을 파이프라인에 편입하고 KubernetesPodOperator로 실행되도록 구성 (모델 개발은 AI 부서, 실행·배포 환경 구축은 본인 담당)
  • GitLab → Jenkins → ECR → Airflow(K8s) 전 구간 배포 자동화 — Jenkins에서 이미지 빌드·ECR 푸시 후 DAG의 이미지 태그를 자동 갱신하도록 구성하여 수동 빌드와 DAG 수정 공수 제거
성과
  • 대응 부서 담당자가 VOC를 인지하는 주기 일 단위 → 1시간 단위, 인지부터 대응 착수까지 평균 반나절 → 1시간 이내 (도입 전후 인지·대응 timestamp 기준 비교)
  • 수집된 VOC가 규칙에 따라 자동 전달되므로, 사람이 취합하는 과정에서 걸러져 몇 개월간 묻히던 건이 구조적으로 사라짐
  • 모델 배포 사이클 80% 단축 (수동 이미지 빌드 · DAG 수정 공수 제거)

데이터 흐름 On-Prem Hadoop(Hive) · Oracle Exadata → EMR(PySpark) → S3(Parquet) → Glue Catalog → Athena
스케줄링Oozie → Airflow

배경 및 문제

On-Premise Hadoop과 Oracle Exadata 기반 정보계를 AWS로 이관하는 과제였다. On-Premise는 클러스터를 24시간 가동해도 비용이 고정이므로 안정성이 우선인 Hive 기반 구성이 합리적인 선택이었으나, 클라우드에서는 수행 시간이 그대로 비용이 된다. 기존 구조를 그대로 옮기면 이관 자체는 성공하더라도 비용 구조가 불리해지는 상황이었다.

대상 워크로드는 DW 100본과 Mart 35본이었고, 이 중 전환·검증 대상으로 수백 줄 규모의 대형 쿼리 5본과 중소 규모 쿼리 30~40본을 선정했다.

기술적 판단
  • Hive를 EMR에 그대로 유지하는 안은 배제 — 이관 리스크는 가장 낮지만 수행 시간이 곧 비용인 과금 모델에서 성능 개선 여지가 없다. PySpark를 선택해 성능 개선이 비용 절감으로 직결되는 구조로 전환. DataFrame API를 쓰는 한 Scala Spark와 실행 성능이 동일하고 유지보수 진입장벽이 낮아 PySpark로 선정
  • 전환 경로를 단정하지 않고 두 가지를 구현해 실측 비교 — (a) DataFrame API 전면 재작성(공수는 크지만 최적화 여지가 큼), (b) HQL을 입력받아 SparkSQL 실행 코드를 자동 생성하는 변환 모듈. 실측 결과 둘이 동일한 실행 계획으로 최적화되어 성능 차이가 없음을 확인하고, 선택 기준을 성능이 아닌 변환 공수와 실행 안정성으로 전환
  • 비용 구조 재설계 — On-Premise 서버 유지 비용을 기준으로, 실제 수행 시간에만 자원이 점유되는 구조를 목표로 절감 수단을 발굴·적용: 워크로드별 executor 차등 배정, Dynamic Allocation 기반 Scale In/Out, EMR Auto-Termination, S3 Storage Tiering, Reserved Instance. Spot 회수 리스크는 노드그룹 분리로 완화 — 온디맨드 1개와 서로 다른 인스턴스 타입의 Spot 노드그룹 여러 개로 구성해 특정 타입의 회수가 잡 전체 실패로 번지지 않도록 구성
  • 출력 포맷을 Parquet(Snappy)로 전환 — Hive는 ORC, Spark는 Parquet에 최적화되어 있어 변경했고, 이 적재 구조가 이후 Athena 분석 환경의 기반이 됨
수행 내용
  • HQL → SparkSQL 자동 변환 모듈 개발 — HQL 스크립트를 세미콜론 단위로 분할해 SparkSQL로 수행되는 Python 실행 파일을 생성하고 실행 변수는 argparse로 주입. 기존 HQL을 그대로 입력하면 PySpark Job으로 수행되어 재작성 공수 없이 엔진 교체 가능
  • Oozie 워크플로 35~40개를 Airflow로 선제 전환 — XML·UI 의존 구성을 Python DAG 코드로 이관해 형상관리 가능한 형태로 전환하면서, 같은 의미(당일 · D-1 · D-2)를 다른 이름으로 쓰던 실행 변수를 표준 이름으로 통일
  • Hive Metastore 대신 Glue Catalog를 메타스토어로 사용하여 Spark와 Athena가 동일한 테이블 정의를 공유하도록 구성
  • 정합성 검증 — 3일치 배치를 대상으로 기존 시스템(Oracle Exadata) 결과값과 row count 및 실제 값을 대조하여 방식별 전환 정확성 확인
  • 호환성 이슈 해결 — 일부 컬럼이 NULL로 반환되는 현상은 Hive와 PySpark의 정규식 이스케이프 규칙 차이로 특정해 개별 수정. Python 2 → 3 제출 시 발생한 타입 오류(LongType 통합)는 POC 단계임을 감안해 타입 코드 전면 수정 대신 런타임 버전을 고정하여 전환 범위 확대를 차단
성과 및 한계
  • 대형 워크로드 처리 시간 3시간 36분 → 52분 (약 4.2배) — 셔플이 반복되는 다단계 집계 구간에서 중간 결과를 메모리에서 처리하는 Spark 실행 방식이 단축의 주된 요인
  • 24시간 상시 가동되던 On-Premise 서버 유지 비용 대비 평균 36% 절감 — 수행 시간 단축과 자원 배정 · Scale In/Out · Auto-Termination · 스토리지 계층화 · 인스턴스 계약 전반의 최적화를 합산한 결과
  • 한계 — Oracle Exadata가 정보계에 깊게 자리잡아 즉시 대체는 불가능했고, Athena를 병행 운영하며 성능·비용을 비교하는 cutover 준비 단계까지 진행했다. 자동 변환 방식(b)도 Hive의 set 구문 미적용과 세미콜론 파싱의 들여쓰기 취약성이라는 제약이 있어, 성능이 동일하다는 실측 결과와 이 제약을 함께 두고 워크로드별 적용 방식을 결정했다

전사 비즈니스 메타 표준화 협의 주관 및 비즈니스 관점 데이터 품질 진단

  • 고객사GS Retail · GS Shop
  • 기간2022.10 - 2023.05 (8개월)
  • 역할표준화 협의 주관 · 메타관리시스템 운영 · 품질 진단
  • 규모전사 범위 · 표준 용어·지표·디멘전 약 500개 · 진단 대상 수천만 row
배경 및 문제

같은 비즈니스 용어와 지표를 부서마다 다른 기준으로 사용하고 있어, 동일한 이름의 지표가 부서에 따라 다른 값을 산출했다. 리포트 수치가 어긋날 때마다 정의를 재확인하는 커뮤니케이션이 반복됐고, 어느 정의가 기준인지 판단할 근거 자체가 없는 상태였다.

상품·고객 마스터는 GS홈쇼핑과 GS리테일이 각각 분리 운영하고 있어, 같은 상품과 같은 고객이 서로 다른 값으로 관리됐다. PK·필수값 등 시스템 제약은 모두 통과하지만 표기만 다른 동일 상품이 서로 다른 상품코드로 중복 등록되고, 동일 고객의 성별·주소·결혼 정보가 계열사 간에 불일치하는 유형이라 기존 품질 검사로는 탐지되지 않았다. (예: '초코파이 4입'과 '초코파이(4입)'이 동일 판매가로 각각 등록되어 병행 사용)

접근 방식
  • 상품명 완전 일치로는 표기 차이로 등록된 동일 상품을 탐지할 수 없다고 보고, 정규화한 상품명을 1차 축으로 두고 판매가·협력사·소싱구분코드를 확증 축으로 조합하여 확신도별 3단 레벨로 분리. 중복 건수만으로는 심각성이 전달되지 않으므로 중복이 유발한 운영 오류(담당MD·상품분류 오매핑)를 별도 레벨로 정량화
  • 표준화 정의서를 산출물로만 남기지 않기 위해 각 부서 확인을 받은 정의만 등재하도록 설계. 다만 표준과 다른 사용을 일괄 금지하면 합의 자체가 막힌다고 보고 사유 제출과 상위 조직장 확인을 조건으로 하는 예외 경로를 함께 마련
수행 내용 — 비즈니스 메타 표준화
  • 부서별로 상이하게 사용되던 용어·지표를 수집하고 정의가 충돌하는 항목을 식별
  • 표준화 협의체를 직접 주관 — 이해관계가 걸린 부서를 모아 공통 정의안을 조율하고 각 부서 및 부서장 확인 절차로 주기적 합의 확보. 표준과 다른 사용 요구는 배제하지 않고 사유와 상위 조직장 확인을 받아 예외 운영하도록 조율하여 표준화 진행과 현업 요구를 동시에 충족
  • 확인이 완료된 정의를 메타관리시스템에 등재해 전사 단일 메타 사전을 구축하고, 이후 운영을 담당하며 신규·변경 용어의 등재 절차 유지
수행 내용 — 비즈니스 관점 데이터 품질 진단
  • 기본 유효성 검증(PK · 필수값 · 형식 · 도메인) 수행
  • 상품 중복 진단 — 판정 기준을 3단 레벨로 설계
    • LV1 · 정규화 상품명 — EC 노출명을 우선 적용(미입력 시 상품명 대체)해 고객에게 실제 노출되는 이름을 기준으로 삼고, 괄호·공백·특수문자를 제거해 정규화한 값으로 그룹핑
    • LV2 · 판매가 · 협력사 · 소싱구분코드 조합 — 후보 그룹 전체가 해당 속성을 공유하는 경우만 채택하고, 조합 수를 늘려가며 확신도를 단계적으로 상승
    • LV3 · 오매핑 탐지 — 동일 상품 판정 그룹 내에서 담당MD 또는 상품분류(대·중·소·세)가 다르게 매핑된 건을 집계하여 중복이 유발한 운영 오류를 정량화
  • 계열사 간 고객 정합성 진단 — CI 회원번호를 허브로 GS리테일·GS홈쇼핑의 동일 고객을 연결해 성별·우편번호·결혼 정보 불일치를 검출. 성별 코드 체계가 계열사 간 상이(M/F ↔ 1/2)하여 정규화 후 비교했고, 값 불일치뿐 아니라 한쪽에만 값이 존재하는 편측 결측까지 대상에 포함
  • 동일 프레임을 계열사별 마스터 구조에 맞춰 이식하여 업무규칙 37건 (상품 34 · 고객 3)으로 정의하고 룰별 위반 row 수를 리포트로 산출, 중복의 근본 원인이 상품 등록 체계 부재임을 제시
성과 및 한계
  • 전사 범위 용어·지표·디멘전 약 500개를 표준 정의로 통합하고 메타관리시스템에 등재
  • 수천만 row 규모 상품 마스터에서 표기만 다른 동일 상품으로 판정된 row가 전체의 약 70% 수준이며 실제 운영에 병행 사용 중임을 확인. 오매핑까지 정량화해 업무 영향을 가시화하고, 이를 근거로 통합 상품 마스터(MDM) 구축의 필요성과 방향성을 결론으로 도출
  • 한계 — 상품명 정규화 기반 판정이라 표기 규칙이 크게 다른 상품은 누락될 수 있고 반대로 정규화 후 이름이 같아도 다른 상품인 경우가 있다. 따라서 70%는 규모를 가늠하기 위한 추정치이며 확정 수치가 아니다. 정확한 확정은 상품을 유일하게 식별하는 체계 없이 불가능하다고 판단해 그 필요성을 MDM 제안의 근거로 삼았다
